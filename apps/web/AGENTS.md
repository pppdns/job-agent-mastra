# apps/web — Next.js UI

- The browser only calls same-origin routes. `src/server/agent.ts` (`server-only`) adds the shared secret and calls the agent. `src/app/api/chat/route.ts` validates `{ threadId, message }` (`src/lib/chat-schema.ts`), builds the agent body in `src/server/chat-body.ts`, and streams `/chat` through; never forward client JSON to the agent.
- Login: only when `APP_PASSWORD` is set (the Fly deployment). `src/proxy.ts` checks the signed `copilot_session` cookie (`src/server/session.ts`) on everything but `/login` and static assets: pages redirect to `/login?next=`, `/api/*` gets 401. Pages that show data live in the `(app)` route group (sidebar layout); `/login` sits outside it, so it never renders chat titles. See [docs/deploy.md](../../docs/deploy.md).
- Chats: `/c/[threadId]` (chat id = Mastra thread id); `src/proxy.ts` redirects `/` to a fresh UUID. Thread list/history/rename/delete go through `src/server/threads.ts`; mutations are server actions in `src/app/actions.ts` that call `refresh()`. Archiving is `archivedAt` in the Mastra thread metadata (`src/lib/thread-archive.ts`; PATCH replaces metadata, so always merge). Archived chats stay fully usable, and `POST /api/chat` unarchives on send. An empty chat focuses its message input (an effect, so it also refocuses when a hidden page is shown again).
- Messages: user text in a `Bubble`; assistant text via Streamdown with images and raw HTML disabled (an injected reply must not make the browser fetch URLs); tool parts as `Trace` rows (`src/components/tool-trace.tsx`); `research_company` renders its `data-research-progress` parts as a timeline plus a findings panel (`research-trace.tsx`, `evidence-list.tsx`); `rescore_jobs` renders `data-rescore-progress` plus a results list (`rescore-trace.tsx`). `globals.css` has an `@source` for Streamdown's classes: restart `next dev` after changing `@source`.
- App tables: server code reads/writes through `@copilot/db` via `appDb()` (`src/server/db.ts`). libsql is synchronous, so pages call `await connection()` before reading (inside `<Suspense>`), or the query would run at prerender time. The same goes for per-request fetches to the agent (e.g. the sidebar's chat list): without it the fetch starts during prerendering, is cut off when the prerender ends, and a surrounding `catch` logs that as a failure.
- Approvals exist only for profile changes the copilot proposes in a chat: `ApprovalCard` reads state from `GET /api/approvals/[id]?threadId=` (404 for other chats) and decides via the `decideApprovalAction` server action with the payload hash it displayed. `/profile` edits are the user's own and apply right away (`editProfileAction` → `editProfile`, with the profile version the page showed; recorded under thread `profile-page`). Above the facts, `PreferencesEditor` edits the structured preferences (home, work mode per place, salary bands, languages, role focus, levels, travel; level dots `LEVEL_DOT`: preferred green, OK neutral, disliked amber, no red) and saves them as one version (`editPreferencesAction` → `editPreferences`, then recent postings are re-screened); the copilot never proposes them. `/profile` shows one card per fact kind, empty ones included (title, hint, accent in `src/lib/profile-kinds.ts`: amber = hard requirement, blue = soft preference, neutral = background), and its History starts collapsed. Job assessments need no approval: `/jobs/[jobId]` shows the current version ("Assessment vN") and earlier versions under a "Version history" toggle that starts closed. At the bottom, `ListingDocument` shows the latest listing snapshot (`latestListingSource`) verbatim in a framed, scrollable document panel, set apart from the derived data above; it renders the stored markdown with images stripped (`withoutImages`) and no raw HTML. Old chats may still contain `propose_job_snapshot` calls; they render as a plain trace row. `/jobs` is a compact, paged table (`aria-label="Jobs"`, 50 rows a page) with URL state `?tab=active|<status>|archived|screened&q=&sort=latest|fit&source=&min=&posted=&unseen=1&top=1&page=` (`src/lib/job-list.ts`; Active = not archived, status tabs exclude archived jobs; `q` uses FTS via `searchJobIds`). Filtering, ordering, paging and the tab counts run in SQL (`listJobsPage`, `jobTabCounts`). Best fit ranks every job on one 0–100 match scale (a with-profile assessment's fit level, else the triage score; then verdict, fewer hard conflicts); the New tab, the inbox of discovered matches, defaults to it. Filters (`JobFilters`): source, minimum match, posted within, unseen only, top only. Row checkboxes and a sticky bar (`JobSelection`, `BulkBar`) shortlist or dismiss many jobs at once (`setJobsStatusAction`). The Screened out tab lists jobs under the triage threshold or not open from home (listing-facts eligibility closed / likely closed, with the deciding quote) and postings the screen dropped (30 days), each with "Keep anyway" (`keepJobAction` / `keepPostingAction`). A banner offers to re-triage discovered jobs triaged against an older profile (`retriageNowAction`: their scores are cleared and a triage-only discovery run starts at once for every job waiting for triage, sent as `triageLimit`, up to `RETRIAGE_MAX_JOBS` (25,000); the rest wait for "Triage next batch" or the next run). Columns: Age, Fit, Status. Color marks decisions that are still open (`src/lib/job-emphasis.ts`): fit (`FitMeter` + a muted `VerdictIcon`; the row stripe follows it) goes grey once applied, closed or archived; the Age pill (`src/lib/job-age.ts`, `AgePill` in `age-pill.tsx`, in the meta line below `sm`) is the listing's age (green ≤ 7 days, amber > 30 days while new/shortlisted/to apply, otherwise neutral) except on the Applied/Interviewing/Offer tabs, where it shows time since the last progress ("In stage", `stageAge` → `progressAge`, see Pipeline below); interviewing rows show the compact round tracker and a note icon when the job has a note; the status pill is plain on single-status tabs. The title link covers the row (pills, icons and the menu sit above it with `relative z-10`); `JobStatusMenu` (also on the job page; shows whose move it is, in one hue: blue tint for shortlisted/to apply/interviewing/offer = your move, quiet with a check for applied = waiting on the employer, plain for new, muted for closed or archived) sets status / (un)archives via `setJobStatusAction` / `setJobArchivedAction`, and marks the job as top or removes the mark (`setJobTopAction`). **Top** is the user's own label beside the status (`top_at`, never set or seen by the copilot): an amber `TopBadge` on list rows and board cards, a star `TopToggle` (optimistic) in the job page header (`top-mark.tsx`). It shows a "Re-score" button when active jobs are stale (`startRescoreAction` starts the run in a new chat, then redirects there).
- **Pipeline** (M21): `/jobs/board` (`ViewToggle` List | Board in the Jobs header) shows non-archived Shortlisted / To apply / Applied / Interviewing / Offer jobs as columns (`listPipelineJobs`, stalest first). Cards (`pipeline-card.tsx`): title link covering the card, company, `ProgressPill`, Top badge, note icon, fit only while shortlisted, `JobStatusMenu` (moving a card = changing status; no drag and drop). `PipelineBoard` (client) lays the columns out as a 5-column grid once the board is ≥ 64rem wide (container query `@5xl`, so an open sidebar counts), else a snapping horizontal scroller with chips that jump to a column (`scrollTo` on the scroller, not `scrollIntoView`, which shifts the page) and mark the visible one. Attention (`progressAge`): time since `progressedAt` (status change or new round); < 7 days plain grey text, 7–13 amber chip with a clock ("follow up"), ≥ 14 red chip ("stuck"), tooltip per status; To apply nudges sooner (amber from 2 days, red from 5: listings close fast; per-stage days in `STAGE`); only that colors anything. `InterviewRounds` (board cards, list rows `compact`, job page): `RoundTrack` segments (done filled, current outlined, upcoming grey, dashed when the total is unknown) plus a menu: "Round N done", next round, total rounds (`setInterviewRoundsAction`, optimistic). The job page shows a Progress strip (pill + rounds) and `JobNotes`: read-only until Edit, Save or ⌘/Ctrl+Enter, Esc/Cancel asks before discarding, `beforeunload` while dirty; `setJobNotesAction` sends the loaded `notesUpdatedAt` and a note saved elsewhere since shows a conflict instead of being overwritten.
- Companies: `/companies/[key]` (key = `companyKey`) lists every role at a company, hidden ones marked, with statuses, fit or triage, and research findings across those roles. Job rows link it as "+N more roles here" when the company has other visible roles; the job page links the company name.
- Recruiter posts (listing facts `recruiter`; `recruiterPost` / `companyLine` in `@copilot/shared`): the board's company is then the agency, so rows, board cards, the digest email and the copilot's job tools show "Acme via Tact" or "Tact (recruiter)" (`companyLine`), and the job page header "Employer not named · via Tact (recruiter)". With the employer unnamed the job page offers no research (the agent's research refuses it too); with it named, research targets the employer.
- Job page header shows "Posted <date> · Added <date>" (`posted` from `getJobDetail`; `~` = approximate, from LinkedIn's "N weeks ago") and links the original listing (`src/lib/listing-links.ts`: canonical URL, then LinkedIn/employer-posting sources, deduped, http(s) only, new tab).
- Discovery: `/discovery` shows source health (last good run, Apify spend vs the monthly budget, model spend of the last 30 days), the runs table (per-source counts, cost, Studio link to the workflow run) and what the screen dropped in the last 7 days. "Run now", "Backfill 7|30 days", "Triage next batch" and "Assess more matches" call `startDiscoveryAction`, which POSTs to the agent's `/discovery/run` with a mode ("Assess more matches" also sends the picked batch size, `ASSESS_BATCH_SIZES` 15/50/200, as `assessLimit`); "Stop run" calls `stopDiscoveryAction` (`/discovery/stop`). Each button has a `Hint` tooltip (what it runs, model or code, rough cost); its per-job costs are constants at the top of `discovery-controls.tsx` that mirror the agent's `budget.ts` reserves, so update both together. A "Last run" panel and the runs table name each run's outcome ("All good", "N problems", "Interrupted", "Failed") from `runOutcome` (`src/lib/run-outcome.ts`), with its problems and failure reasons. While a run is going the page refreshes 3 s after the previous refresh finished, only while the tab is visible (`RefreshWhileRunning`; never overlapping, so a slow server isn't buried under renders), and shows `RunProgress` (`discovery-run-progress.tsx`: the steps, each source done/running/waiting, the current step's count and a linear time-left estimate, `estimateRemainingMs` in `src/lib/run-eta.ts`) from the run's `progress`. Status icons and colors are shared in `discovery-status.tsx` (tones from `TONES`). `/settings/search` (`SearchSettingsForm`) saves with `saveSearchSettingsAction` and re-screens recent postings at once (`rescreenPostings`). On `/jobs`, discovered jobs carry their source badges (`postingSourcesByJob`), a "New" badge until opened, and, until they get a full assessment, a `TriageScore` pill with the triage reason as the row's second line ("Triage pending" before triage); Hidden ones (screened out, under the triage threshold) never reach the list (`listJobs` applies `visibleJobs`). The job page shows a "Quick triage" card (score, reason, and "Assess fully" while there is no assessment: `assessJobAction` → the agent's `POST /jobs/:jobId/assess`, about 30 s), a "Seen on" list of the job's postings with links to each board, and marks the job seen from a client effect (`MarkSeen` → `markJobSeenAction`), not during render, so prefetching never marks a job seen. The sidebar's Jobs item shows the unseen-match count (`unseenMatchCount`, read in `AppSidebar`). The runs table shows each run's funnel (triaged, matches, assessed, email status, what stopped it early) and its estimated cost split into Apify, triage and assessments (`runCost`, `src/lib/run-cost.ts`, from `modelSpendByRun`, so a running run's cost grows live); `/settings/search` also holds the triage threshold, assessments per run, triage cap and model spend cap.
- Assessments at a glance: `assessment-visuals.tsx` holds the shared pieces (verdict badge, fit meter, signal chips, evidence badge, summary header) and the tone map. Colors come from semantic tokens in `globals.css` (`success`, `warning`, `info`, `destructive`, plus muted); use these, not raw Tailwind colors. A successful `save_job_draft` renders as `AssessmentCard` ("Saved · vN") (from the validated tool input) instead of a trace row; the copilot is told to keep its prose short because of it. Its "Research next" buttons (`research-suggestions.tsx`, topics from `suggestedResearchTopics`) send `researchRequestText` in the chat (disabled while a reply runs); on the job page the same buttons call `startResearchAction`, which starts the research in a new chat like Re-score.
- Durable runs: `useChat({ resume: true })` reconnects via `GET /api/chat/[threadId]/stream` (204 when nothing runs); Stop calls `POST /api/chat/[threadId]/stop` before closing the stream. Sidebar markers (`thread-run-markers.tsx`, logic in `src/lib/run-markers.ts`): the thread list polls `GET /api/run-status` (latest run per chat + server clock) every 3 s; spinner while running, a dot for a reply that ended (completed, or failed/interrupted in red) after the chat was last opened. "Last opened" lives in `localStorage` (`copilot:chat-seen`, server-clock ms); chats never opened in this browser count as seen at its first load. Stopped runs get no dot. The poll also refreshes the list when a run starts in an unlisted (new) chat and when a run ends. Observational Memory `data-om-*` parts: compaction ones render as a line (`compaction-line.tsx`), the rest are hidden.
- Technical panel: `technical-panel.tsx` (sheet in the chat header) reads `GET /api/threads/[threadId]/usage` (`threadUsage` + approvals from `@copilot/db`). Studio links: `${AGENT_URL}/traces?traceId=…` (`serverEnv()` derives `AGENT_URL` from `AGENT_PORT`).
- Next keeps visited pages mounted but hidden (React Activity): a chat keeps streaming when you navigate away, and e2e locators must filter `{ visible: true }`. e2e runs with `WEB_MODE=fixture`. Verify UI in a foreground browser: a hidden built-in browser pane can leave streamed pages on their Suspense fallback. Wait for a reply to finish before sending the next message: the input ignores submits while busy.
- Sentry: `src/instrumentation.ts` (server + edge, `onRequestError`), `src/instrumentation-client.ts`, shared options in `src/lib/sentry.ts`, and `app/global-error.tsx`. It's on only in production builds with `NEXT_PUBLIC_SENTRY_DSN` (inlined at build: the Fly image). Errors caught and swallowed need `Sentry.captureException`. See [docs/deploy.md](../../docs/deploy.md#sentry).
- `src/server/env.ts` validates server env lazily, so `next build` doesn't need secrets.
- Cache Components and Partial Prefetching are on (Next 16.4 defaults). Read `node_modules/next/dist/docs/` before using data-fetching or caching APIs.
- UI: shadcn/ui (Radix Nova). `src/components/ui/` and `src/hooks/use-mobile.ts` are CLI-owned (don't edit; `ui/` is excluded from Biome). `SidebarMenuSkeleton` uses `Math.random()`, which breaks prerendering: use `Skeleton` with fixed widths; add or update with `pnpm dlx shadcn@<version> add <component>`. Chat composition follows the `shadcn` skill (`rules/chat.md`).
- Tests: Vitest for units; Playwright in `e2e/` (`playwright.config.ts` starts an isolated mock stack using system Chrome). Spec files share one database; `rescore.spec.ts` re-scores every stale job, so it runs in its own project after the rest.
- **Chips** (`src/lib/job-chips.ts` → `jobChips`, rendered by `src/components/job-chips.tsx`): a job's at-a-glance facts from its verified listing facts (`app_jobs.facts`), the eligibility code decided, and the structured preferences. Line 1 always: work mode (with the place that includes home, office days), pay (the listing's figures, compact; tinted by the salary bands after a rough conversion, `@copilot/shared` `salary.ts`), level when known. Line 2: the assessment's labelled points (`summary.fitChips`: hard conflicts red; strengths green and weaknesses amber only with a quote `saveDraft` verified; older drafts without labels show a conflict count), main languages, role focus, travel, employment type, hours (at most 5, then "+N"). Colors only carry meaning: preference levels (preferred green, OK neutral, disliked amber, no red), pay vs bands, eligibility (closed red; unclear amber). Dashed with "?" = not confirmed by the listing; filled = worth attention (great pay, staff+ levels). Each chip is a button with the listing's words in its tooltip; the job page's "At a glance" lists them all ("From the listing"). Shown on `/jobs` rows (right under the title), the hidden list, company pages and the job page; the chat card keeps its salary label (it has no facts).
